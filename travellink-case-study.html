01 — Overview

What is TRAVEL LINK?

TRAVEL LINK is a national tourism intelligence platform developed by the Big Data Institute (BDI) under Thailand's Ministry of Digital Economy and Society. It aggregates data from across Thailand's tourism ecosystem — hotels, attractions, visitor trends — and presents it to a diverse set of stakeholders: government agencies, tourism operators, and researchers.

When I joined the project, the platform had solid data underneath, but the experience on top of it was fragmented and difficult to use. My role was to redesign the full product — from the public-facing website to the internal admin portal — while shipping new features in parallel.

The core challenge

TRAVEL LINK serves three user types — General, Government, and MOU — each with a different verification path and access level. The original registration treated them all the same, leaving Government users unsure how to verify correctly and MOU users confused about why their access wasn't working.

02 — Problem

A registration flow that felt like a wall

TRAVEL LINK serves three distinct user types, each with different access levels and verification paths. Understanding these differences was the foundation of the redesign.

👤
General User
Can register through any channel — email, Google, or Microsoft. No special verification required. Access is granted immediately with standard privileges.
🏛️
Government User
Must register using an email on an officially registered government domain. Once the domain is verified, government-level access privileges are granted automatically. Includes public academies.
🤝
MOU User
Can register through any channel (email, Google, or Microsoft), but remains at standard access until an OrgAdmin or MOU Admin within their organisation explicitly approves them.

General users had no significant friction. The challenge lay in the other two types — Government users needed to register with a verified government email domain, which the old form didn't clearly communicate. MOU users, meanwhile, had no way of knowing their access was pending admin approval, leaving them confused about why their privileges differed from other users.

Problem Statement

How might we design registration flows that clearly communicate what each user type needs to do — and what to expect next — so that Government users complete domain verification correctly, and MOU users understand their access is pending approval rather than broken?

03 — Research

Understanding where and why people dropped off

Before touching any wireframes, I needed to understand the failure points in depth. I combined qualitative methods with direct stakeholder input to map the full picture.

1
Stakeholder Interviews
Spoke with the BDI team and platform administrators who handled manual verification. They described receiving incomplete or incorrect registrations daily — users filling in wrong information, skipping required fields, or simply abandoning mid-flow. Approval queues were backed up because it was hard to tell what was missing.
2
User Flow Audit
Walked through the existing registration end-to-end, documenting every screen, decision point, and error state. Found too many steps in a flow that could be significantly shorter, with fields that appeared for all users regardless of type, and error messages that were generic ("please try again").
3
Competitive Review
Reviewed registration flows from similar government digital platforms in Thailand and internationally — looking at how progressive disclosure, contextual help, and multi-tier verification were handled elsewhere.
4
User Feedback Collection
Gathered qualitative feedback from users who had attempted registration. Three themes emerged consistently: confusion about which user type they belonged to, uncertainty about what was expected from them at each step, and distrust when the system gave no clear confirmation or status update.

Key Insights

😵 Users didn't know which tier they were
  • User type selector had no descriptions
  • Government vs operator distinction unclear
  • Wrong tier = incorrect or missing information submitted
📋 Required information was unclear upfront
  • No upfront overview of required information
  • Users encountered unexpected fields mid-flow
  • Often abandoned the form rather than completing it
💬 Feedback unclear after submission
  • Confirmation message was vague and easy to miss
  • No visibility of approval status after login
  • Users unsure if submission went through — resubmitted multiple times
⚙️ Admins overwhelmed by bad data
  • Incomplete or incorrect registrations daily
  • Had to email back for missing info
  • No admin tools to flag or request docs
04 — Design Process

From one broken flow to three guided journeys

The core design decision was to split registration into three distinct, adaptive paths — one per user tier — using progressive disclosure so users only ever see what's relevant to them, at the right moment.

Information Architecture

I restructured the entire flow starting from a clear first question: "Who are you registering as?" Each answer branches into a tailored path. Steps that aren't needed simply don't appear.

1
Choose user tier (with descriptions)
Each option now includes a short plain-language description: what type of user this is for, what access they'll get, and what documents they'll need. Users can make an informed choice before proceeding.
2
Required information shown upfront
Before any form fields, users see a clear overview of what information they'll need to complete registration. No surprises mid-flow. This helped users come prepared and reduced abandonment.
3
Adaptive form — only relevant fields
Each tier has its own condensed field set with only relevant fields shown. Real-time validation flags issues immediately rather than at the end, so users can correct mistakes before they become blockers.
4
Confirmation + status tracking
After submitting and accepting the terms consent, users receive a confirmation email immediately — containing their account details and guidance on how to get started with the platform. Once logged in, users can see their current approval status directly in the interface, so they always know where they stand without needing to contact support.
5
Admin portal: review and request tools
The admin side was redesigned alongside user-facing flows. Admins can now review registrations, flag issues, and follow up with users directly from the portal — closing the loop between users and reviewers.

05 — Outcomes

Qualitative results & feedback

While we didn't have pre/post analytics set up for quantitative measurement, the qualitative signal from internal review and user feedback was clear.

— User feedback, post-launch

📉
Fewer incomplete submissions
Admin team reported a significant drop in incomplete or incorrect registrations — attributing it to the upfront information overview and clearer in-form guidance.
⏱️
Faster admin review
The new admin portal tools reduced back-and-forth communication. Reviewers could flag issues and follow up with users directly from the portal without switching tools.
💬
Positive user feedback
Users described the new flow as clearer, more reassuring, and less intimidating — particularly the confirmation step which had previously been absent.
🏗️
Foundation for future features
The redesigned architecture and component library now serves as the foundation for ongoing feature development across the platform.
06 — Reflection

What I learned

What worked well

Starting with the admin pain points — not just user-facing ones — was the right call. When admins are overwhelmed by incomplete or incorrect registrations, fixing the clarity upstream directly reduces their workload downstream. Designing both sides together was the breakthrough.

What I'd do differently

I'd push harder to set up basic analytics before launch. Qualitative feedback is valuable, but having conversion data at each step would have helped us prioritise faster and make a stronger case for future iterations.

Key design principle

Progressive disclosure is powerful — but only when you've truly understood the user's mental model first. The tier structure only worked because we invested time understanding how each group thinks about their own identity and access needs.

Constraints & tradeoffs

Government platforms come with real institutional constraints — approval chains, legacy systems, legal requirements. Learning to design within these boundaries without compromising the user experience was one of the most valuable skills I developed here.
